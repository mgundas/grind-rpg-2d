# Phase 4 — Items and Economy: implementation plan

Scope: `GAME_DESIGN.md` §6.3, §7 and §12 Phase 4 only. Plan produced after reading `AGENTS.md`, `PROGRESS.md`, `DECISIONS.md`, the current codebase, and the installed Colyseus 4.0.31 schema / Drizzle 0.45.4 typings.

## 1. What already exists and what this phase builds on

**Foundations to reuse**

- **DB/service pattern:** `apps/server/src/db/schema.ts` has `accounts`, `characters`, `sessions`; `characters.gold` already exists and is loaded into `CharacterRecord`, but is never written by the room. Services take an injected `Db` and use `db.transaction`. Migrations are committed SQL generated by drizzle-kit (D001, D021).
- **Room architecture:** `MapRoom.ts` has a fixed tick (`input → AI → combat → regen → respawns → spawns → warps`), Zod `safeParse` handlers that drop bad messages, per-runtime save chains, direct owner-only messages (`selfStats`), and view-tagged `players`/`monsters` collections with 4 Hz interest management.
- **Combat:** `resolvePlayerSwing` / `resolveMonsterAttack` are pure functions over player + monster runtimes. `physicalAttack()` already accepts `weaponAttack` (currently 0); `defenseOf(vit)` is VIT-only. Monster deaths bubble through `emitSwing`, where XP is awarded. `KilledMonster` carries `typeId`, position and killer session; `getMonster()` gives `goldMin`, `goldMax`, `dropTableId`.
- **RNG seam:** `ServerServices.createRandomSource` is crypto-backed in production and seeded in tests. Drop rolls must use it.
- **Data package:** Zod-validated JSON modules loaded as TypeScript source, with id/reference validation and deterministic map generation.
- **Client:** Zustand store as the Phaser↔React bridge, draggable `Window` component, `CharacterWindow` pattern for keybinds, `session.ts` typed message listeners and `requestStats` on bind, procedural layered character art via one canvas texture key, and placeholder icon support.
- **Tests:** pure shared/data tests, `@colyseus/testing` room tests with injected fake services, and real-Postgres tests gated on `TEST_DATABASE_URL`.

**Greenfield**

- No `items`, `item_log`, `gold_log` tables; no item repository or services.
- No item/drop/shop/NPC JSON; all monster `dropTableId` values are `null` and `packages/data/test/monsters.test.ts` asserts that.
- No ground-item state, pickup, ownership, inventory/equipment, hotbar, NPC dialog, shops, warehouse, return scroll, or gold award.
- Combat ignores equipment; `PlayerState` has no equipment visual fields; character art only knows class/gender/hair.
- Tiled `npc` objects are parsed but unused; only `blacksmith` exists on the village map.

**Library facts verified**

- `@colyseus/schema@4.0.31` supports `"uint32"` / `"float64"` fields and `MapSchema`; ground items can be another `@view()`-tagged collection like monsters.
- `drizzle-orm@0.45.4` supports `jsonb()` and partial unique indexes (`.where(sql...)` in `pg-core/indexes.d.ts`).
- React 19 with no drag-and-drop library: inventory drag uses native pointer events. Phaser 4 already uses canvas textures for layered characters.

## 2. Architecture decisions

1. **Memory is the live authority; the DB is written per operation.** While online, `PlayerRuntime.inventory` is authoritative. Commands are validated against it, persisted in one DB transaction, then applied and broadcast. No tick blocking, no 60-second batch window.
2. **Per-player command queue.** Every inventory/economy command runs through `runtime.inventoryChain` (analogous to `saveChain`). Two clicks on one ground item, split-vs-move, or buy-vs-sell cannot interleave.
3. **Full inventory snapshots, not deltas.** Owner-only `inventory` messages carry gold, 90 cells and 8 equipment slots. Small (≈10–15 KB worst case), revisioned; stale snapshots are ignored.
4. **Gold is not part of `CharacterSave`.** `characters.gold` is written only by transactional gold operations (pickup gold, buy, sell), avoiding autosave overwrites. Gold is loaded with the inventory.
5. **Items are DB rows from the moment they exist.** Drops are inserted as `location='ground'` before becoming visible in state. Pickup is a conditional `UPDATE ... WHERE location='ground'`, making duplicate pickup impossible.
6. **Warehouse is account-scoped.** Inventory/equipment use `owner_character_id`; warehouse uses `owner_account_id` with 3 pages. Character deletion cascades inventory/equipment but not warehouse items.
7. **Both inventory pages are always open** (the spec allows this); warehouse has 3 pages.
8. **Four visible equipment categories for now:** weapon, armor, helmet, shield. Shoes/bracelets/necklaces/earrings give stats only.
9. **Hotbar is client-side**, persisted per character in `localStorage` as `slot → item definition id`. The server receives `useItem {instanceId}`.
10. **Drops:** ownership = highest damage contribution, owner-only 30 s, then free-for-all; items despawn after 2 min. Ground gold is a world drop, not an instant credit.
11. **NPCs stay static map objects.** The server validates proximity and `npcId` from `MapAssets`.
12. **Starter kit:** every new character gets a class-appropriate tier-1 weapon (equipped), 5 small HP potions, and 500 gold.

## 4. Hard systems: exact approach and edge cases

### 4.1 Inventory and item transactions

**Model:** 2 pages × 5×9 = 90 top-left indexed cells; each item occupies one column and `size` vertically. Equipment indexes 0–7 from `EQUIP_SLOTS`; warehouse 135 cells. Items are referenced by UUID.

**Validation path:** `applyInventoryCommand(runtime.inventory, command, definitions)` is pure and returns the next state plus a DB mutation plan. The room calls the injected repository inside the per-player chain. The DB transaction re-checks ownership/location.

**Edge cases**
- Page boundary: size 3 at row 7 must not cross pages.
- Swap only when both items fit at each other’s top-left slots.
- Equip swap must fit the unequipped item back into the source slots.
- Unequip with a full inventory rejected; item stays equipped.
- Class/level requirements server-validated.
- Stack merge respects `maxStack`; leftover stays in source; split creates a new UUID and logs.
- Commands serialized per session; reject when runtime is gone.
- Kick/warp awaits the queue before saving/reserving.
- On load, overlaps/invalid slots are repaired and logged.

### 4.2 Drops and ownership

- Roll gold then items in table order with the room RNG; seeded tests.
- Ground items are inserted **before** entering `WorldState`.
- Owner = highest damage contributor (`damageBy` map), fallback killer; owner-only 30 s, then anyone.
- Despawn 2 min; 1 s tick removes state and rows; insert retry once then skip with a log.
- Drop position 12–24 px arc, snapped to walkable (fallback monster position).
- Stale ground rows purged on room creation for that map and at boot.

### 4.3 Equipment stats

- Aggregate item stats computed on equipment change and stored on the runtime; all derived values recompute in one place.
- Max HP/MP decreases clamp current values, never kill.
- Level-up/stat allocation pass the same bonuses; tests cover it.
- `physicalAttack` uses weapon attack; monster damage uses VIT defense + armor defense.
- `PlayerState` mirrors four layer keys; empty string means none.

### 4.4 Consumables and return scroll

- `itemUseReadyAtMs` 500 ms cooldown.
- Full HP/MP does not consume; dead/warping cannot use.
- Return scroll: consume → `beginWarp` → on failure re-insert the same UUID and restore snapshot (tested compensation).

### 4.5 Shops and warehouse

- Prices from data only; client prices ignored.
- Buy validates shop, NPC proximity, quantity, affordability and space before debit.
- Sell validates inventory ownership, not equipped, `sellPrice > 0`.
- Warehouse account-scoped, NPC proximity, account lock in transaction.

### 4.6 Client UI

- React overlays capture pointer events.
- Drag/drop uses pointer capture; server rejects invalid drops and the UI snaps back on the next snapshot.
- `requestInventory` on bind handles the join-message race.
- Missing icons generated at Preload from `items.json`.
- Ground-item sync reads the view-filtered collection each patch.

## 7. Risks and mitigations

1. **Duplication from concurrent clicks** → per-session queue + conditional ground update + PK/unique indexes; double-pickup tests.
2. **Gold overwritten by autosave** → gold excluded from `CharacterSave`; transactional gold ops only.
3. **Tick blocking** → all DB work async; drops persisted on a side queue; tick never awaits.
4. **Kick/warp racing an item write** → await `inventoryChain` before save/reserve.
5. **Wrong stats after equip/level-up** → one `recomputeDerived()` path; tests.
6. **Ground-item ghosts after crash** → insert before visibility; cleanup on boot/room create; despawn tick.
7. **Data drift** → Zod at import + cross-reference tests.
8. **Scope creep into Phase 7** → upgrade levels/bonuses/blacksmith effects stay inert and documented.
9. **Client state races** → full revisioned snapshots + `requestInventory` on bind.
10. **Texture cache explosion** → key includes only four equipped layers; compare before `setTexture`.
11. **Inventory repair hiding data loss** → repairs logged to `item_log`.
12. **Large `MapRoom.ts`** → new logic in `rooms/items.ts`, `rooms/drops.ts`, `rooms/groundItems.ts`, `items/*`.
